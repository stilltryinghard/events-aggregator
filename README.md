# Events Aggregator

Сервис-агрегатор поверх Events Provider API. Раз в сутки забирает события провайдера в собственную базу и отдаёт их через свой REST API: со списком, фильтром по дате и пагинацией. Свободные места запрашивает у провайдера с кэшем на 30 секунд, регистрацию и отмену проксирует провайдеру и хранит у себя оформленные билеты.

Развёрнутый сервис: https://stilltryinghard-events-aggregator.dev-2.python-labs.ru

Стек: Python 3.12, FastAPI, SQLAlchemy 2.0 (async, asyncpg), Alembic, PostgreSQL, httpx, pytest, Ruff, uv, Docker.

## Запуск локально

```bash
cp .env.example .env
# в .env вписать свой EVENTS_PROVIDER_API_KEY
docker compose up --build
```

Приложение поднимется на `http://localhost:8000`, документация на `http://localhost:8000/docs`. Миграции применяются автоматически при старте контейнера (`run.sh`), сразу после старта запускается первая синхронизация.

### Переменные окружения

| Переменная | Назначение |
|---|---|
| `POSTGRES_HOST`, `POSTGRES_PORT`, `POSTGRES_USERNAME`, `POSTGRES_PASSWORD`, `POSTGRES_DATABASE_NAME` | подключение к PostgreSQL |
| `EVENTS_PROVIDER_URL` | адрес Events Provider API |
| `EVENTS_PROVIDER_API_KEY` | ключ для заголовка `x-api-key` |

Пробелы по краям значений срезаются автоматически.

## API

| Метод и путь | Что делает | Коды ответа |
|---|---|---|
| `GET /api/health` | проверка сервиса и подключения к базе | 200 |
| `POST /api/sync/trigger` | ручной запуск синхронизации | 200 (`ok` или `already_running`) |
| `GET /api/events?date_from=&page=&page_size=` | события из локальной базы | 200, 400 |
| `GET /api/events/{event_id}` | детали события со схемой мест | 200, 404 |
| `GET /api/events/{event_id}/seats` | свободные места, кэш 30 секунд | 200, 400, 404 |
| `POST /api/tickets` | регистрация на место | 201, 400, 404 |
| `DELETE /api/tickets/{ticket_id}` | отмена регистрации | 200, 400, 404 |

Ошибки валидации запроса отдаются как 400, а не стандартные для FastAPI 422, в соответствии с контрактом задания.

## Устройство

```
app/
├── api/           роуты, схемы ответов, сборка зависимостей
├── usecases/      бизнес-логика и протоколы зависимостей
├── repositories/  работа с базой (паттерн Repository)
├── clients/       клиент Events Provider API и пагинатор
├── entities.py    сущности, с которыми работает бизнес-логика
├── models.py      ORM-модели
├── worker.py      фоновая синхронизация
└── cache.py       кэш свободных мест
```

Зависимости направлены сверху вниз: роуты вызывают юзкейсы, юзкейсы зависят только от протоколов (`typing.Protocol`), реализации которых подставляются в `app/api/dependencies.py`. Бизнес-логика не импортирует ни SQLAlchemy, ни httpx. Клиент провайдера переводит JSON в сущности, репозитории переводят ORM-модели в сущности, поэтому формат провайдера и схема базы не просачиваются в юзкейсы.

### Синхронизация

- Запускается сразу после старта приложения и затем раз в сутки фоновой задачей в lifespan FastAPI, а также вручную через `POST /api/sync/trigger`.
- Инкрементальная: провайдеру передаётся дата `last_changed_at` последней успешной синхронизации, первая синхронизация идёт с `2000-01-01`.
- Страницы обходит `EventsPaginator`, асинхронный итератор поверх курсорной пагинации провайдера.
- События и площадки сохраняются через upsert (`INSERT ... ON CONFLICT DO UPDATE`): провайдер принимает дату без времени и присылает часть событий повторно, повторная запись безопасна.
- Каждый запуск записывается в журнал `sync_runs` со статусом `running`, `success` или `failed` и текстом ошибки.
- Одновременно может идти только одна синхронизация: частичный уникальный индекс на `sync_runs` не даёт вставить вторую строку со статусом `running`. Это защищает от параллельных запусков из нескольких подов и от повторных вызовов `trigger`. Зависшие запуски старше часа помечаются упавшими.
- Метаданные из ТЗ хранятся в `sync_runs`: `last_sync_time` это `started_at`, `sync_status` это `status`, `last_changed_at` под своим именем.

### Билеты

- Перед обращением к провайдеру проверяются статус события, дедлайн регистрации и существование места по `seats_pattern`.
- Отменённый билет не удаляется, а помечается `cancelled_at`, история регистраций сохраняется.
- Провайдер переиспользует `ticket_id` для одного и того же места. Поэтому первичный ключ билета свой, а уникальность `ticket_id` обеспечивается частичным индексом только среди активных билетов.

## Тесты и линтер

```bash
uv run pytest
uv run ruff check .
uv run ruff format --check .
```

Клиент провайдера и пагинатор покрыты юнит-тестами с `unittest.mock`, без сети и базы. В CI линтер и тесты запускаются до сборки образа, деплой без их прохождения не выполняется.

## Принятые решения и ограничения

- Айди событий и площадок провайдера используются как первичные ключи. Это упрощает upsert и запросы к провайдеру, но при подключении второго источника событий схему придётся расширить.
- Статус события хранится строкой, а не перечислением: провайдер может присылать новые статусы (например, `finished`), и синхронизация не должна на них падать.
- Фильтр `date_from` считает начало суток по UTC.
- Провайдер не сообщает об удалённых событиях, поэтому они остаются в локальной базе.
- Кэш свободных мест живёт в памяти процесса, у каждого пода свой.
- Если провайдер принял регистрацию, а сохранение билета в базе упало, место у провайдера останется занятым без записи у нас. Решение: компенсирующая отмена у провайдера при ошибке сохранения.
- При одновременном старте нескольких подов миграцию накатывает один из них, остальные могут один раз перезапуститься, после чего стартуют нормально.
